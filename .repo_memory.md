## Architecture and ownership

### Builtin Codex vs extension Codex

- Fact: Builtin Codex is server-only; `codex-ext` is the registered Codex extension at `extensions/codex_ext` with type `codex_ext`.
- Why it matters: platform logic and extension logic are intentionally separate, so changes for Codex extension behavior should target `codex-ext`, not the builtin server-only Codex path.
- Citations: `extensions/extensions.json:3-17`; `agent_log_server/server.py:8041-8049`

### Live Codex extension path

- Fact: The only live registered Codex extension path is `extensions/codex_ext`; `extensions/codex` was removed as dead code and tooling/package data now target `codex_ext`.
- Why it matters: this avoids editing the wrong extension tree and keeps schema/runtime work aimed at the path that the loader actually instantiates.
- Citations: `extensions/extensions.json:3-18`; `pyproject.toml:38-41`; `scripts/codex_schema_extract.py:5-6,86,155`

### Codex auth surface today

- Fact: Codex protocol/runtime include account auth schemas, but current `codex` and `codex-ext` clients only use model/thread/turn RPCs and do not call account methods yet.
- Why it matters: auth-related work still needs explicit client wiring; the schemas existing upstream does not mean the local extension already uses them.
- Citations: `extensions/codex_ext/protocol.py:172-179,281-288,313`; `extensions/codex_ext/runtime_protocol.py:594-675,819-842,1314-1320`; `extensions/codex_ext/client.py:303-305,328,437-543`

### Session picker binding

- Fact: Extension `session_picker` fields are rendered by `static/modals/settings_schema.js`, and `server.py` binds `settings.session` as a one-time thread/session selection.
- Why it matters: session binding behavior is shared and schema-driven, so new session-picker logic should plug into the existing modal/server path instead of inventing extension-specific selectors.
- Citations: `agent_log_server/static/modals/settings_schema.js:298-327,512-514`; `extensions/copilot_sdk/settings_schema.json:15-20`; `extensions/codex_ext/runtime_protocol.py:1194-1201`; `agent_log_server/server.py:5977-6005`

### Extension settings independence

- Fact: Codex extension settings must be fully schema-driven and must not depend on hidden builtin-Codex modal inputs for save or hydrate.
- Why it matters: the builtin Codex settings block is intentionally not the extension settings path. Future modal/save work must treat extension schema fields as the source of truth so extension settings remain independent and old builtin state does not overwrite extension-managed values.

### Extension availability

- Fact: Extension availability is driven by `enabled && dependency_ok`; inactive extensions stay out of agent dropdowns while splash settings show `dependency_message`.
- Why it matters: readiness and UX gating already have a single contract, so new dependency/auth checks should feed that pipeline instead of creating a second availability system.

### Legacy codex removal

- Fact: Legacy builtin codex (`app_server` shellspec, `codex-legacy` dropdown entry) has been removed. The legacy shellspec no longer exists; only `app_server_observed` remains in `agent_log_server/shellspec/app_server.yaml`. The agent dropdown in `ui_flow.js` no longer offers `codex-legacy`.
- Why it matters: Any code path that tries to start the legacy `app_server` spec will error out. The 7 legacy call sites in `server.py` (`_get_or_start_appserver_shell()`) are now dead-on-arrival. Do not try to resurrect or reference the legacy spec.
- Citations: `agent_log_server/shellspec/app_server.yaml`; `agent_log_server/static/js/codex_agent/settings/ui_flow.js:395-400`

### codex-ext-exp shellspec isolation

- Fact: `codex-ext-exp` has its own shellspec at `extensions/codex_ext_exp/shellspec/app_server_exp.yaml` pointing at the patched binary (`~/downloads/codex/codex-rs/target/debug/codex-app-server`). Transport label is `"app-server:codex-experimental"`, spec IDs are `app_server_exp` and `app_server_exp_observed`. This is fully isolated from `codex-ext` (which uses `"app-server:codex-extension"` and `app_server_observed`).
- Why it matters: `codex-ext-exp` runs a separate app-server process from `codex-ext`. There is no process adoption between them. The patched binary supports `developerInstructions` in `TurnStartParams` for mid-thread developer instruction updates.
- Citations: `extensions/codex_ext_exp/shellspec/app_server_exp.yaml`; `extensions/codex_ext_exp/transport.py:20,382,388`; `extensions/codex_ext_exp/manifest.json:10-12`; `worktrees/notes/PATCHED_APP_SERVER.md`

### Copilot CLI process CWD isolation

- Fact: CopilotClient singleton in `extensions/copilot_sdk/client.py` now explicitly sets `cwd` to `$HOME` to prevent the CLI process from inheriting the framework-shell launch CWD (typically TE2/mrselect6). Without this, the CLI reads AGENTS.md from the inherited CWD and injects the wrong repo's instructions into every conversation. Per-session `workingDirectory` handles repo-specific context.
- Why it matters: The agent_log_server is launched as a TE2 framework shell, inheriting TE2's CWD. The Copilot CLI reads AGENTS.md from its process CWD at startup and bakes it into the system prompt foundation. This caused TE2-internal instructions (WBA, etc.) to leak into conversations in unrelated repos.
- Citations: `extensions/copilot_sdk/client.py:1791`; `extensions/copilot_sdk/_vendor/copilot/client.py:186,1291`

## Critical contracts

### Composer draft restore

- Fact: Failed sends restore drafts server-side via `meta["draft"]` + `draft_update` only when an extension returns `restore_draft: true`; visible failure uses the shared error contract.
- Why it matters: send-failure UX is backend-owned and opt-in, which avoids duplicate user-turn artifacts and keeps draft restoration consistent across extensions.
- Citations: `agent_log_server/server.py:6565-6706,7523-7624`; `extensions/__init__.py:1320-1335`; `TRANSCRIPT_CARD_CONTRACTS.md:269-290`

### Conversation error contract

- Fact: User-visible conversation errors use live `type: "error"` and replay `role: "error"`; `rpc_error` is reserved for app-server pending-RPC failures.
- Why it matters: extensions and frontend rendering need one visible error contract for live and replay parity; `rpc_error` is not the generic user-facing lane.
- Citations: `TRANSCRIPT_CARD_CONTRACTS.md:222-248`; `extensions/copilot_sdk/router.py:1459-1496`; `agent_log_server/static/js/codex_agent/events/router.js:196-199`

### Token/footer ownership

- Fact: Footer token/context is backend-owned: routers must emit `context_window` in `token_count` / `token_usage`; frontend must not do extension-specific recovery.
- Why it matters: footer correctness depends on the backend delivering complete token metadata, so frontend patches should not try to reconstruct missing extension fields.
- Citations: `TRANSCRIPT_CARD_CONTRACTS.md:71-116`; `extensions/copilot_sdk/router.py:179-222`

### Transcript replay roles

- Fact: Legacy Codex rich replay for tool usage depends on transcript roles `mcp_tool` and `web_search`, not flattened `command` rows.
- Why it matters: replay fidelity for Codex tools still depends on those transcript role shapes, so router/storage changes must preserve them.
- Citations: `agent_log_server/server.py:4692-4816`; `agent_log_server/static/codex_agent.js:3134-3251`

### Runtime transport

- Fact: Runtime UI/backend contracts must stay Socket.IO-only; do not add HTTP fallbacks without explicit user approval.
- Why it matters: this is a repo-level architectural rule, especially for shared harness behavior and extension runtime contracts.
- Citations: `AGENTS.md:69-78`

### Socket.IO namespace patterns

- Fact: The repo already uses `python-socketio` `AsyncServer`, `AsyncClient`, `AsyncNamespace`, and multiple namespaces like `/appserver` and `/sidebar_ipc`.
- Why it matters: This is a durable architectural fact about the existing transport stack. It will help future work choose repo-native IPC designs and avoid inventing a parallel transport when namespace/client patterns already exist in this codebase.
- Citations: `agent_log_server/server.py:136-153,3635-3700`; `te2_services/appserver_transport.py:37-110,265-280`; `requirements.txt:3`

### Framework-shell secret pattern

- Fact: Both the main server and `mcp_agent_pty_server.py` derive a stable repo-root-based framework-shell secret from `~/.cache/framework_shells/runtimes/<fingerprint>/secret`.
- Why it matters: This is the framework-shell trust mechanism already present in the repo. It is useful background for process isolation work, but it is separate from the dedicated app-server IPC secret used for KB-origin Socket.IO notifications.
- Citations: `agent_log_server/server.py:3287-3314`; `mcp_agent_pty_server.py:28-50`

### IPC auth secret

- Fact: The private `/ipc` Socket.IO namespace uses a dedicated random secret stored at `~/.cache/app_server/ipc_secret` via `agent_log_server/ipc_auth.py`.
- Why it matters: KB-origin repo-memory delta notifications authenticate with this local cache-backed secret instead of reusing the framework-shell secret. This keeps the app-server IPC path simple and scoped to the new namespace.
- Citations: `agent_log_server/ipc_auth.py`; `agent_log_server/server.py`; `mcp_agent_pty_server.py`

### Ask-user interaction IDs

- Fact: `agent-pty-blocks.ask_user` uses the conversation's own `conversationId` (from `CONVERSATION_ID` env var injected at MCP stdio launch) as the canonical `requestId`. No derivation, no hashing, no side-band registration. Each MCP server process is 1:1 per conversation and ask_user is synchronous per thread, so `conversationId` is collision-free. The old `canonical_ask_user_request_id()` hash helper and `_ASK_USER_REQUEST_ID_RE` regex have been removed.
- Why it matters: ask-user cards render with `requestId = conversationId`, the MCP tool registers its pending future under the same key, and the `/ipc ask_user_response` event resolves it by matching that key. Future ask-user work must use this conversationId contract and must not reinvent ID generation, side-band registration, or hash derivation.
- Citations: `mcp_agent_pty_server.py:2357-2449`; `extensions/codex_ext/router.py:1916,2494,2803`; `extensions/codex_ext_exp/router.py:1916,2494,2803`; `extensions/codex_ext/transport.py:656`; `extensions/codex_ext_exp/transport.py:656`; `extensions/codex_ext/runtime_protocol.py`; `extensions/codex_ext_exp/runtime_protocol.py`; `extensions/copilot_sdk/te2_runtime.py`

### Ask-user live bind seam

- Fact: Live Codex/Codex-exp `agent-pty-blocks.ask_user` calls bind on the `item/started` notification carrying an `item.type == "mcpToolCall"` tool item, not on an emitted `item/tool/call` server-request in the tested runtime path.
- Why it matters: ask-user card synthesis must follow the same live MCP tool-call parsing path as other MCP tool cards in the Codex routers. Assuming a live `item/tool/call` request for this path breaks binding, leaves `meta.json` empty, and causes the MCP tool to hang waiting for a response path that was never created.
- Citations: `extensions/codex_ext/transport.py:654-700`; `extensions/codex_ext/router.py:1737-1938,2411-2484`; `extensions/codex_ext_exp/transport.py:654-700`; `extensions/codex_ext_exp/router.py:1737-1938,2411-2484`; `/data/data/com.termux/files/home/.cache/framework_shells/runtimes/b4f2d44683b344a8/0a37fcbc242ec454/logs/fs_1774985801_bdf1da55.stderr.log:141-143`

### Resume/send virtual ack

- Fact: `codex-ext` thread resume treats `thread/status/changed` `idle` as virtual ack and fails fast on `mcp_startup_update` with `status.state = failed`.
- Why it matters: successful resume is event-first, not giant-response-first, so future resume fixes should preserve that transport behavior instead of waiting on the full `thread/resume` payload.
- Citations: `extensions/codex_ext/transport.py:857-923,1016-1030`; `extensions/codex_ext/client.py:371-397,1019-1023`

### TE2 relay passthrough

- Fact: The TE2 appserver relay only forwards Socket.IO events that have explicit `on_<event>` passthrough methods; missing `on_get_runtime_options` broke proxied schema dynamic selects even though the direct `:12359` portal worked.
- Why it matters: proxy-only UI failures can come from the TE2 relay shim dropping an otherwise-valid appserver event, so future debugging should compare direct portal behavior against the relay passthrough table before changing frontend logic or the reverse proxy.
- Citations: `te2_services/appserver_transport.py:163-179`; `agent_log_server/server.py:361-369,789-796`; `agent_log_server/static/modals/settings_schema.js:95-103,457-492`

### TE2 proxy rewrite

- Fact: The live TE2 `proxy_shell` can rewrite absolute `/api/...` references inside served JavaScript and inject Socket.IO path adjustments, so exact source-string checks are not proxy-safe for runtime-option detection.
- Why it matters: direct `:12359` behavior can differ from proxied `:8089` behavior because the wrapper changes the delivered asset shape, so future fixes should reason about the live proxy path and match runtime sources by path shape/suffix instead of the unproxied literal.
- Citations: `/data/data/com.termux/files/home/mrselect6/app/apps/codex_agent/manifest.json:15-33`; `agent_log_server/static/modals/settings_schema.js:67-105,481-484`; User input: It works fine from Port :12359 it only fails on 8089

### Assistant markdown render split
- Fact: Assistant markdown now uses SMD only for live token streaming; once finalized, assistant cards are rendered through the markdown-it event renderer, and static/replay assistant cards also use markdown-it.
- Why it matters: underscore-heavy file paths and markdown links remain stream-friendly during live generation but finalize to the safer renderer, preventing malformed anchors and emphasis corruption in transcript cards.
- Citations: `agent_log_server/static/js/codex_agent/markdown.js:310-338`; `agent_log_server/static/js/codex_agent/assistant_stream.js:11,78`; `agent_log_server/static/codex_agent.js:3043`; `agent_log_server/static/codex_agent.js:3658`

### Codex response schema registry

- Fact: Codex runtime response schemas are keyed by lowercase method names in `runtime_protocol`, and missing response entries can be rebuilt from the loaded schema definitions / schema bundle on demand.

### Context compaction routing

- Fact: Context compaction is initiated by a generic SIO `compact` event from the frontend; `server.py` routes it through `ext_loader.compact_session()` for extension-owned conversations. Codex extensions use `thread/compact/start` RPC (must be in `_CLIENT_RESPONSE_METHODS`); copilot-sdk uses `session.rpc.compaction.compact()`.
- Why it matters: compact was broken because `thread/compact/start` was missing from the schema whitelist and the server routed all compact requests to the legacy builtin app-server. Both the schema registration and the routing must be correct for compaction to work.
- Citations: `extensions/codex_ext/runtime_protocol.py:52`; `extensions/copilot_sdk/client.py:2493-2507`; `extensions/__init__.py:1375-1380`; `agent_log_server/server.py:8000-8049`

### Patched codex app-server binary

### Copilot assistant.message envelopes

- Fact: Copilot SDK can emit empty `assistant.message` tool-request envelopes; only `assistant.message` events with real content should finalize transcript cards before tool rows.

### Resume virtual ack timing
- Fact: Codex conversation resume still follows the lazy `turn/start -> thread/resume -> turn/start` fallback, but the `thread/resume` virtual-ack leg can complete well after 10 seconds while app-server startup/auth noise is still settling; both `codex-ext` and `codex-ext-exp` now wait 30 seconds for that resume leg.
- Why it matters: if this timeout is shortened or misdiagnosed as a bind-only problem, message send fails before the retrying second `turn/start` even though the app-server does eventually emit `thread/status/changed idle` and the successful `thread/resume` result.

### FWS pipe reader contract
- Fact: Pipe-backed shell consumers in this repo must treat framework-shells as the owner of stdout consumption: use `subscribe_output()` / `subscribe_output_bytes()` for reads and `write_to_pipe()` for stdin writes, not direct `state.process.stdout.read(...)` loops.

## Search discipline

### Do not blindly content-search bundled or generated trees

- Fact: Do not run blind recursive file-content searches through high-noise bundled/generated roots in this repo; use name-only listing there and narrow to specific source trees before searching contents. ## Repo memory harness

### Canonical repo memory backing file

- Fact: Repo memory is backed by `.repo_memory.md`, and the shared prompt-context loader discovers it from the logical repo root before appending it to developer instructions.
- Why it matters: repo memory injection is now a real runtime seam, so future memory-related work should update this file-backed path instead of inventing a second source.
- Citations: `agent_log_server/prompt_context.py:9-20,34-103,123-143`

### KB registration

- Fact: `.repo_memory.md` is registered in the KB config so the KB tool surface and prompt-injection surface point at the same backing file.
- Why it matters: editing repo memory through KB and injecting repo memory into prompts now target the same durable artifact.
- Citations: `.agent-pty.toml:4-5`

### KB root

- Fact: KB root now follows the harness launch cwd/repo root; `kb_reload_config()` no longer switches repos via cwd override.
- Why it matters: KB scope is tied to the active project root at launch, so agents should not attempt to re-scope KB to a different repo mid-session.
- Citations: `mcp_agent_pty_server.py:63-95,3301-3364`; `extensions/copilot_sdk/te2_runtime.py:15-59`; `KB_MEMORY_MCP.md:25-28,105-106,160`

### KB mutation model

- Fact: KB mutations are patch-style edits; `confirm_hash` is a legacy no-op and the `hash` shown in KB read headers is informational only.
- Why it matters: agents should not add extra compare-and-swap bookkeeping for normal KB writes. Use `dry_run` when a preview is useful, but do not treat KB edits as requiring explicit hash coordination.
- Citations: `mcp_agent_pty_server.py:3913-3981,3985-4038,4041-4084`; `KB_MEMORY_MCP.md:72-102,145-150`; `AGENTS.md:238-243`

### Do not ask to restart harness server
- Fact: Do not ask to restart the live harness server in this repo; the active agent session is running on that server, and restarting it kills the harness connection.
- Why it matters: ask-user and live debugging work stall if the agent tells the user to restart the very backend the harness depends on. In this setup, restart requests are off-limits unless the user explicitly chooses that disruption.
- Citations: `mcp_agent_pty_server.py`; `User input: STOP ASKING ME TO RESTART THE SERVER, YOUR HARNESS IS ON THIS SERVER. ### Keep local harness rules repo-scoped
- Fact: Workspace-local harness rules in this repo (for example not restarting the live harness server) belong in repo-local docs/memory only and must not be copied into downstream consumer or third-party extension guidance.
- Why it matters: downstream-facing docs should describe portable install/update behavior for consumers, while this repo's live-harness constraints are specific to how the agent session is hosted here. Mixing those scopes leaks local assumptions into external guidance and produces the wrong instructions.
- Citations: `User input: Why did you put... The "you not restarting" The server rule is a LOCAL REPO rule... Not a downstream consumer rule....`; `User input: There's a difference between DOWNSTREAM CONSUMERS AND THIS WORKSPACE... DO YOU UNDERSTAND THAT?`

## Markdown link routing

### Markdown file links route through TE2 open

- Fact: Markdown-rendered file-path links in transcript cards are intercepted in the frontend and routed through the same `te2_agent_open` Socket.IO flow used by TE2 diff/view cards, not left as plain browser navigation.
- Why it matters: file links in assistant/user markdown now open in the host editor with the existing sidebar/IDE pipeline instead of navigating the iframe away from the transcript.
- Citations: `agent_log_server/static/js/codex_agent/markdown.js:109-142`; `agent_log_server/static/codex_agent.js:1894-1953`; `agent_log_server/server.py:993-1003`

### Markdown external links use backend xdg-open

- Fact: Markdown-rendered `http/https` links are intercepted in the frontend and sent over Socket.IO to backend `open_external_url`, which validates the URL and launches it with `xdg-open`.
- Why it matters: external citations now open through the device/browser opener path without adding HTTP fallback routes or relying on default iframe anchor navigation.
- Citations: `agent_log_server/static/js/codex_agent/markdown.js:120-125`; `agent_log_server/static/codex_agent.js:1924-1953`; `agent_log_server/server.py:1006-1045`

### Markdown file links parse line and column metadata

- Fact: Markdown file links support `#L123`, `#L123C4`, and `path:line[:column]` parsing before dispatch, and the parsed `{ path, line, column }` target is forwarded into the TE2 open request.
- Why it matters: rendered file references preserve editor jump location instead of sending a raw `#L...` suffix as part of the file path.
- Citations: `agent_log_server/static/js/codex_agent/markdown.js:8-33`; `agent_log_server/static/js/codex_agent/markdown.js:64-98`; `agent_log_server/static/js/codex_agent/markdown.js:127-132`; `agent_log_server/static/codex_agent.js:1941-1948`
